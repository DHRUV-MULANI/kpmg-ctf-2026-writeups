# KPMG CTF — "Locks of Confusion - 1" Writeup

**Challenge:** Locks of Confusion - 1 (Web)
**Target:** `https://kicyber-deea1f3c3f67-locks-of-confusion1-0-0.chals.io/`
**Result:** `KPMG_CTF{iUfLNLka3pq4XXfreGWQn8dz8UqF534jAtlVuXlSsPAi}`

---

## TL;DR

An internal ops portal exposes a fictional migration story around a 2007 Debian
4.0 "etch" host (`legacy-03`). A `/verify` CAPTCHA-like gate guards access to an
`/archive/` area. Passing it issues a *signed Flask session cookie* that unlocks
two tarballs:

1. a partial tape restore of `legacy-03` from 2007, containing the
   `svc-legacydb` `authorized_keys` (an RSA-2048 public key), and
2. a keyspace of 300 candidate private keys generated by the **Debian OpenSSL
   predictable-PRNG bug (CVE-2008-0166)**.

One of the 300 keys matches the deployed public key (`privkey_0137.pem`).
A `README.txt` in the keyspace explains that a leftover `user.txt` backup is
password-protected, and that the ZIP password is the **first 64 characters of
the base64 body** of the matching PEM file. That yields the flag.

## 1. Reconnaissance

### 1.1 Portal discovery

The root serves an "Internal Ops Portal" (`Werkzeug/2.2.2`, `Python/3.11.2`,
header `X-Served-By: ops-gw01`). A quick `ffuf` run plus manual browsing found:

| Path | Purpose |
|---|---|

| `/tickets` | `TICK-4471` references archive paths for a 2007 tape restore |
| `/docs` | `MIG-2011-004` — 2011 P2V migration of `legacy-03` to `ops-gw01` |
| `/backups` | backup list; row referencing "legacy-03 provisioning state" |
| `/archive/...` | protected archive area (403 unless verified) |
| `/wiki/notes` | misc notes |
| `/robots.txt` | disallows `/internal-only/`, `/old-admin/`, `/.git/`, `/archive/keyspace/README.txt` |

`robots.txt` even carries a hint comment:

> don't leave the inventory just because you didn't find the SoUrCe

### 1.2 Story clues (this is a key-recovery narrative)

- `legacy-03` = **Debian 4.0 "etch"**, provisioned **2007-11-14**.
- The `svc-legacydb` service account keypair was created during that original
  2007 provisioning (checklist step 4.2) and **never rotated**, surviving the
  P2V migration in 2011.
- A 2007 tape bundle (`legacy-03-2007.tar.gz`) and a keyspace mirror
  (`legacy-keys-2007.tar.gz`) exist under `/archive/`.

A 2007 Debian system generated SSH keys with **openssl 0.9.8c-4** — the version
affected by **CVE-2008-0166**, where the OpenSSL RNG was reduced to ~15 bits of
entropy → only **32 768 possible ssh-rsa keys**. This is the "locks of
confusion" — the key was "decided long before it was ever generated".

### 1.3 The `/verify` gate

The two tarballs return:

```
HTTP/1.1 403 Forbidden
Content-Type: text/plain
Vary: Cookie
...
complete the access check at /verify first
```

`/verify` presents an access check:

> Before pulling anything from `/archive/`, click the node labeled **NAME** in
> the diagram below.

- The target **node name is dynamic** (we observed `lb-02`, `web-01`,
  `dns-01`, `legacy-02`, `db-03`, ...).
- `/verify/image/<nonce>` returns a random 640x360 network diagram containing
  **6 blue node circles** (RGB ~ `#121212` vs. background), each paired with a
  light-gray text label (sometimes above, sometimes below the circle).
- Clicking calls `POST /verify/check` with `{"nonce", "x", "y"}`; wrong clicks
  do not invalidate the nonce (repeated attempts are allowed).

```html
<p class="lead">
  Before pulling anything from <code>/archive/</code>, click the node
  labeled <strong>legacy-02</strong> in the diagram below.
</p>
...
var nonce = "e4ad4b7339c53918cd7c62b0156e580e";
...
fetch("/verify/check", { method: "POST",
  headers: {"Content-Type": "application/json"},
  body: JSON.stringify({nonce: nonce, x: x, y: y}) })
```

## 2. Solving `/verify` programmatically

### 2.1 Approach

Because the target name changes on every request, the solver must, per request:

1. Parse the target name from `<strong>…</strong>` and the `nonce`.
2. Fetch the diagram image.
3. Find the 6 node circles by blue-colour segmentation (component analysis).
4. OCR each node's label (tesseract with a lowercase/digit/`-` whitelist, on an
   inverted 20x upscaled crop; search bands above **and** below the circle).
5. Pick the node whose OCR text is closest (Levenshtein) to the target.
6. Click the **circle center** (the accepted hit region is the circle; labels
   are just visual hints).

OCR quirks observed: `lb-02` reads as `1b-02`, `web-01` as `webh-01`, etc. —
the Levenshtein ranking handles that.

`solver: scripts/verify_solve7.py`

Extract from a successful run:

```
[attempt N] target='web-01' nonce=6d20c88afb3642ed5a20e35319c1d475
    node (169,114) ocr={'8': 'weh-02', ...} -> (2, 'weh02')
    node (330,152) ocr={'8': 'webh-01', ...} -> (1, 'webh01')
...
VERIFIED target=web-01 node=(330,152) point=(330,152) res={"ok":true}
```

### 2.2 The unlock is a signed session cookie

The check response sets a cookie — note the **`Vary: Cookie`** header on the
403 page, which was the clue that the gate is cookie-keyed:

```
POST /verify/check -> 200 {"ok":true}
Set-Cookie: session=eyJhcmNoaXZlX2FjY2Vzc191bnRpbCI6MTc5MTY4Nzk4Ny4zMjI1ODk0fQ.asr62w.SY0C7COPKfgV0BecRyStELZmyYM; HttpOnly; Path=/
```

Decoding the first segment (Flask session payload, itsdangerous-signed):

```json
{"archive_access_until": 1791687987.3225894}
```

So a successful click issues a **Flask session cookie** that unlocks
`/archive/` for "the next few minutes". Replaying the same request with the
cookie jar immediately after verification succeeds (see
`scripts/verify_and_fetch.py`).

## 4. Matching the deployed key against the keyspace

Compute the *public key fingerprint* for each candidate and compare with the
deployed key's fingerprint:

```bash
$ ssh-keygen -lf legacy-03-2007/home/svc-legacydb/.ssh/authorized_keys
2048 SHA256:Qavw4d6sGmzyN4XIc2mt9CPHs980Q1FU6B0j3qxnIIo no comment (RSA)

$ for f in privkey_*.pem; do
    fp=$(ssh-keygen -l -f "$f" | awk '{print $2}')
    [ "$fp" = "SHA256:Qavw4d6sGmzyN4XIc2mt9CPHs980Q1FU6B0j3qxnIIo" ] && echo "MATCH: $f"
  done
MATCH: privkey_0137.pem
```

**`privkey_0137.pem`** is the private key whose public half is the live
`svc-legacydb` key. (All 300 keys are unique 2048-bit RSA keys from the
predictable-key space.)

## 5. The `user.txt` backup & ZIP password

The keyspace `README.txt` (by "M. Reyes, infra") explains a leftover backup:

> there's also a leftover account-data backup ... never cleaned up:
>
>     /archive/backups/e6f25638ae2ed6ba955cdae6a74c6798.zip
>
> it's password-protected ... the password is the BODY of the matching .pem
> file — not the full file, not the header/footer lines, just the base64 block
> in between ... strip the "-----BEGIN...-----" and "-----END...-----" lines
> and every line break from what's left, and take the first 64 characters.

The archive is downloaded the same way (fresh verify cookie):

```
GET /archive/backups/e6f25638ae2ed6ba955cdae6a74c6798.zip -> 200 (249 B, application/zip; contains user.txt)
```

Deriving the password from `privkey_0137.pem`:

```python
import re
body = re.sub(r'-----BEGIN [A-Z ]*KEY-----|-----END [A-Z ]*KEY-----', '',
              open('privkey_0137.pem').read())
body = body.replace('\n', '').replace('\r', '').replace(' ', '')
pw = body[:64]
# -> MIIEowIBAAKCAQEAui2yyUzRtrahcJ1ZpfIrOBvT+s9ZI4k0mXQMegwGWfeKQ4cA
```

Unlocking and reading `user.txt`:

```python
import zipfile
z = zipfile.ZipFile('e6f25638ae2ed6ba955cdae6a74c6798.zip')
print(z.read('user.txt', pwd=pw.encode()).decode())
```

## 7. Root cause / lessons

1. **Never reuse a compromised key generation scheme.** The
   CVE-2008-0166 predictable keyspace means any RSA key generated by vulnerable
   Debian OpenSSL versions can be brute-forced (32 768 candidates) and the
   private key recovered from the public key alone.
2. **Rotate keys on migration.** The 2011 P2V migration (MIG-2011-004) carried
   `svc-legacydb`'s original 2007 keypair forward instead of rotating it.
3. **`Vary: Cookie` as a signal** — the archive 403 responses advertise that
   access state is cookie-derived, which pointed to the session-cookie unlock.
4. **The gateway itself was the first lock**: an OCR-solving, simulation-aware
   gate on the diagram's node labels — an image-CAPTCHA flavor that must be
   parsed (dynamic target name + node labels) rather than brute-forced.
